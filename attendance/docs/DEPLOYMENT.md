# Deployment guide

The cloud part is **one container** (API + worker + owner PWA) plus a **managed PostgreSQL 16** database. A Singapore
region is recommended for low latency from Malaysia.

> Status: deployable code and configuration are complete. **Nothing has been deployed yet.** That needs your hosting,
> database, domain and email accounts (listed below).

## What you need (external accounts / credentials)

| Need | Example providers | Used for |
|---|---|---|
| Container hosting with HTTPS | Render (Blueprint included: `render.yaml`), Fly.io, Railway, Google Cloud Run, any VPS with Docker + Caddy | API + PWA |
| Managed PostgreSQL 16 | Neon, Supabase (as plain Postgres), Render Postgres, AWS RDS, DigitalOcean | Data |
| Domain name | Any registrar (.com / .my) | `https://attendance.yourdomain.com` |
| Transactional email | Resend (API key) or any SMTP (Amazon SES, Mailgun, Brevo, Google Workspace SMTP relay) | Notifications |
| Android signing keystore | Generated by you with `keytool` | Signing APKs and updates |
| GitHub repository with Actions | GitHub | Building the APK in CI |

## Step by step (Render + Neon example)

1. **Database**: create a Neon project (region Singapore) with database `attendance`. In its SQL editor run
   `deploy/db-roles.sql` with your own strong passwords.
2. **Secrets**: generate the template key: `openssl rand -base64 32` → `TEMPLATE_KEYS=1:<value>`.
3. **Email**: create a Resend account, verify your sending domain (SPF/DKIM DNS records), and create an API key.
4. **Hosting**: Render → New → Blueprint → select this repository (`attendance/render.yaml`). Fill the `sync: false`
   variables:
   - `PUBLIC_BASE_URL=https://attendance.yourdomain.com`
   - `DATABASE_URL=postgres://att_app:...@<neon-host>/attendance?sslmode=require`
   - `MIGRATION_DATABASE_URL=postgres://att_owner:...@<neon-host>/attendance?sslmode=require`
   - `TEMPLATE_KEYS`, `EMAIL_FROM`, `RESEND_API_KEY`
   Migrations run automatically at boot (`MIGRATE_ON_START=true`, serialized with an advisory lock).
5. **Domain**: add the custom domain in Render and create the CNAME record. TLS is issued automatically.
6. **Verify**: `https://attendance.yourdomain.com/readyz` → `{"ok":true}`. Check the logs: there must be **no**
   "Row-level security is NOT enforced" warning.
7. **Create your restaurant**: open the URL on your phone → Create account. Then set `SIGNUP_ENABLED=false` if this is
   a private single-restaurant installation.
8. **Email test**: Settings → Notifications → Send test email. The delivery log must show `sent`.
9. **Kiosk**: build/install the APK ([APK_INSTALL.md](APK_INSTALL.md)), then pair it using Devices → Add kiosk.

## Any Docker host

```bash
cd attendance
cp .env.example .env    # fill in real values
docker build -t attendance .
docker run -d --name attendance --env-file .env -p 8080:8080 --restart unless-stopped attendance
```
Put an HTTPS reverse proxy in front (e.g. Caddy: `attendance.example.com { reverse_proxy localhost:8080 }`) and set
`TRUST_PROXY=true`. SSE needs proxy buffering off (Caddy/Render handle this; for nginx set `proxy_buffering off;` on `/api/stream`).

> The Dockerfile has not been built in the development environment (no Docker daemon there). CI covers the server and
> web builds it relies on.

## Local development

```bash
# PostgreSQL 16 running locally
bash attendance/scripts/dev-db.sh                      # creates roles + DB + runs migrations
cd attendance/server && npm ci
DATABASE_URL=postgres://att_app:app_pw@localhost:5432/attendance_dev \
TEMPLATE_KEYS="1:$(openssl rand -base64 32)" EMAIL_TRANSPORT=log npm run dev
cd ../web && npm ci && npm run dev                      # Vite proxies /api to the server
```
Tests: `cd attendance/server && TEST_PG_ADMIN_URL=postgres://postgres@localhost:5432/postgres npm test`.

## Scaling notes

- Several instances are safe: realtime uses LISTEN/NOTIFY (every instance hears every commit), and the worker claims
  work with `SKIP LOCKED`. You may also run the worker in only one instance (`RUN_WORKER=false` elsewhere).
- SSE keeps one connection per open dashboard. Plan about 1 DB connection per instance for LISTEN, plus the pool (10).
- Key indexes: events by `(restaurant_id, event_time)`, sessions by `(restaurant_id, check_in_at)` and `(employee_id, check_in_at)`.

## Publishing a kiosk update

1. Build a signed release with a higher `kioskVersionCode` (CI `workflow_dispatch` inputs, or locally).
2. Upload the APK to an HTTPS location you control (e.g. object storage / CDN). It must stay available.
3. Register it: `cd attendance/server && MIGRATION_DATABASE_URL=... npm run create-release -- --apk app-release.apk --url https://downloads.example.com/kiosk-1.1.0.apk --version-code 2 --version-name 1.1.0 --cert-sha256 <signing cert SHA-256> --notes "..."`
4. Kiosks show "Update available". A manager approves the install on the device. See [APK_INSTALL.md](APK_INSTALL.md).

## PWA updates

Deploying a new container publishes the new PWA. `index.html`, `sw.js` and the manifest are served `no-cache`, hashed
assets are immutable, and `/api/*` is `no-store` and never cached by the service worker. Open dashboards show
"New version available — Reload".
